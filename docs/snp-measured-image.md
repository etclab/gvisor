# Minimal measured guest image

Ticket 06. A guest image an operator can enumerate by hand — firmware, kernel, initrd, and a
read-only dm-verity-protected root filesystem, and nothing else — built so that every covered
byte is a byte in the launch measurement.

Vocabulary is `CONTEXT.md`. Builds on `docs/snp-host-stack.md` (ticket 01) and on
`docs/adr/0004`–`0006`. Scripts are in `docs/snp/image/`.

---

## Result, in one paragraph

The image is five files: `OVMF.fd`, `vmlinuz`, `initrd.img`, `cmdline.txt`, `rootfs.img`.
The root filesystem is a squashfs with a dm-verity hash tree appended and its root hash on the
kernel command line; the initrd is 21 entries the build lists by hand; the root filesystem is
6 files and 13 applet links, all listed with hashes in the manifest the build emits. It boots, maps the root
through verity with `panic_on_corruption`, mounts the config device read-only and `noexec`,
proves on the serial console that no writable path is executable, and runs the embedded
binary. Flipping one byte of the root filesystem or the root hash on the command line panics
the guest before the byte is used. **One finding with consequences beyond this ticket:
ticket 01's firmware does not measure the kernel, initrd or command line at all** — see
[Firmware](#firmware-the-kernel-was-not-measured-under-ticket-01s-ovmffd). The image uses a
different firmware build, and the launch adds `kernel-hashes=on`.

The confidential boot was run once by the operator (it needs root for `/dev/sev`): the guest
reports `SEV: Status: SEV SEV-ES SEV-SNP` and `SNP running at VMPL0`, `sev-guest` loads and
the report interface appears, and the boot is otherwise line-for-line the control boot.
Console, manifest and QEMU command line are in `docs/snp/image/evidence/`.

## What is in the image

| File | Role | How it enters M |
|---|---|---|
| `OVMF.fd` | `OvmfPkg/AmdSev/AmdSevX64` at `edk2-stable202502` | measured directly, first |
| `vmlinuz` | AMDESE guest kernel `6.16.0-snp-guest-038d61fd6422` (ticket 01's, unchanged) | SHA-256 in the firmware's hashes table |
| `initrd.img` | 21 entries, listed below | SHA-256 in the hashes table |
| `cmdline.txt` | the `-append` string, verbatim | SHA-256 in the hashes table |
| `rootfs.img` | squashfs + verity hash tree | transitively, via `verity.roothash=` on the command line |

Everything else on the QEMU command line — disks, network, serial — is outside the
measurement. Two launch parameters that are *not* files also move it: the vCPU count (one
measured VMSA page per vCPU) and the SEV policy. The launch script fixes both (`-smp 4`,
policy `0x30000`); ticket 07 must take them as inputs.

### Initrd (`gen_init_cpio` list, verbatim from the manifest)

```
dir /dev 0755 0 0
nod /dev/console 0600 0 0 c 5 1
dir /proc 0755 0 0
dir /sys 0755 0 0
dir /newroot 0755 0 0
dir /bin 0755 0 0
dir /sbin 0755 0 0
dir /lib 0755 0 0
file /init init 0755 0 0                      docs/snp/image/init.initrd
file /bin/busybox busybox 0755 0 0            Ubuntu busybox-static 1:1.36.1-6ubuntu3.1
slink /bin/{sh,mount,umount,insmod,cat,echo,sleep,switch_root} busybox
file /sbin/veritymap veritymap 0755 0 0       docs/snp/image/veritymap.c, static
file /lib/dm-bufio.ko  0444                   from the guest kernel build
file /lib/dm-verity.ko 0444                   from the guest kernel build (CONFIG_DM_VERITY=m)
```

The archive is generated by the kernel tree's own `usr/gen_init_cpio` from that list, with
`-t 0`, so no root is needed to create the device node and the timestamps are zero.

`/init` does four things and hands over: find the root device by virtio-blk serial
(`attested-rootfs`), load dm-verity, create the mapping from the command-line parameters,
mount the root read-only, mount the config device (serial `attested-config`, `ro,noexec,
nosuid,nodev`, tolerated absent), `switch_root`. `veritymap` exists because the initrd has no
`dmsetup`: it is a hundred lines of device-mapper ioctls with the verity table spelled out, so the
mapping is auditable rather than assembled by a library.

### Root filesystem

```
/bin/busybox                       static, same binary as the initrd
/bin/{sh,mount,umount,insmod,cat,echo,sleep,ls,dmesg,grep,sed,poweroff,sync} -> busybox
/sbin/init                         docs/snp/image/init.rootfs
/usr/bin/tunneld                   build parameter TUNNELD; placeholder until ticket 14
/etc/attested-tunnel/author.pub    derived from build parameter AUTHOR_KEY, 64 hex chars + newline
/lib/modules/tsm_report.ko         report interface (ticket 01's evidence path)
/lib/modules/sev-guest.ko
/config /proc /sys /dev /run /tmp  mount points, empty
```

`mksquashfs -comp zstd -all-root -mkfs-time 0 -all-time 0 -root-time 0`; then `veritysetup
format --no-superblock` with the hash tree appended to the same file at the first block after
the data. No superblock, so every parameter the kernel needs — block size, block count, hash
offset, root hash, salt (none) — is on the measured command line rather than read from the
unmeasured disk:

```
console=ttyS0 earlyprintk=serial panic=-1 rdinit=/init
verity.roothash=<64 hex> verity.salt=- verity.datablocks=339 verity.hashstart=339
```

`/sbin/init` mounts `/proc`, `/sys`, `/run`, `/tmp` and `/sys/kernel/config` all
`nosuid,nodev,noexec`, loads `tsm_report` and `sev-guest`, walks `/proc/mounts` and reports
any mount that is `rw` without `noexec`, prints the mount table, runs `/usr/bin/tunneld`, and
powers off when it exits. There is no getty, no shell listening anywhere, and nothing else to
run.

The busybox is Ubuntu's `busybox-static`, pinned by package version and hash. It is a
general-purpose multi-call binary — `busybox wget` works if invoked by that name — and it is
the one input here that a reviewer cannot enumerate by eye. A busybox built from source with
a trimmed applet set would close that; it was not done because the binary is a pinned distro
artifact whose provenance is at least as auditable as anything built here, and the applet
list an attacker could reach is only useful with code execution the image gives no path to.

## Firmware: the kernel was not measured under ticket 01's `OVMF.fd`

Ticket 01 built `OvmfPkg/OvmfPkgX64.dsc`, as AMDSEV's `common.sh` does, and
`docs/snp-host-stack.md` states that the measurement changes if the kernel, initrd or command
line changes. **That is not true of that firmware.** The mechanism by which a direct-boot
kernel enters an SEV measurement is specific:

1. QEMU, only when the `sev-snp-guest` object has `kernel-hashes=on`, computes SHA-256 of the
   kernel, initrd and command line and writes them into a page inside the firmware image
   (the area the firmware advertises under GUID `7255371f-3a3b-4b04-927b-1da6efa8d454`)
   before `LAUNCH_UPDATE` measures that memory. (`target/i386/sev.c`, `sev_add_kernel_loader_hashes`:
   "Only add the kernel hashes if the sev-guest configuration explicitly stated kernel-hashes=on".)
2. The firmware, when it loads those blobs from fw_cfg, checks each against the table and
   refuses one that is absent or wrong. That check is `BlobVerifierLib`. `OvmfPkgX64.dsc`
   links `BlobVerifierLibNull`, which accepts everything. `OvmfPkg/AmdSev/AmdSevX64.dsc` links
   `BlobVerifierLibSevHashes`, which returns `EFI_ACCESS_DENIED` when the table is missing or
   the hash does not match.

Without (1) nothing about the kernel is in M; without (2) the host can swap the kernel after
the measurement is taken and the firmware will load it. Ticket 01's launch had neither. Its
"identical across three boots" observation is consistent with this — the measurement was a
function of the firmware and the VMSAs alone.

So the image carries `OVMF.amdsev.fd`, built by `docs/snp/image/build-ovmf-amdsev.sh` from
the same edk2 tag into the same local prefix as a separate file (ticket 01's `OVMF.fd` is
untouched, and is still what the control boot uses). The launch script adds `kernel-hashes=on`.

Two consequences worth stating:

- **The AmdSev firmware cannot boot the image outside SNP.** With no `sev` object there is no
  hashes table, so every fw_cfg blob is refused and the boot manager falls through to the grub
  image the firmware embeds, which then fails to find a disk. That is correct fail-closed
  behaviour, and it is why `launch-measured-guest.sh -no-snp` substitutes ticket 01's
  non-verifying `OVMF.fd`: the control boots the same kernel, initrd, command line and root
  filesystem, under a different firmware.
- **The firmware contains a grub image that is never used.** `AmdSevX64.fdf` embeds one
  unconditionally, built at firmware build time by `grub-mkimage` from the host's grub modules.
  Its bytes are in M. Its provenance is therefore recorded (`grub-efi-amd64-bin
  2.12-1ubuntu7.3`), and one deviation from the edk2 tree is recorded with it: Ubuntu's grub
  does not ship `linuxefi.mod` or `sevsecret.mod`, so the build script removes those two names
  from `OvmfPkg/AmdSev/Grub/grub.sh`'s module list and leaves the change visible to `git
  diff` in the tree. A firmware whose measured bytes depend on the host's grub package is a
  reproducibility cost; a firmware that does not verify the kernel is a soundness cost.

`docs/snp-host-stack.md` was not edited — that is ticket 01's record — but its "Things that
will bite" claim about the measurement moving with the kernel should be read with this section.

## The config device

Outside the measurement, by design (ADR-0004, ADR-0005). A raw ext4 image (no journal,
`root_owner=0:0`, label `attested-config`), attached as a read-only virtio-blk device with
serial `attested-config`, mounted by the initrd at `/config` with `ro,noexec,nosuid,nodev`.
`docs/snp/image/mkconfigdev.sh SRCDIR OUT.img` packages a directory; no root needed.

**Layout — this is the interface ticket 15 writes to and tunneld reads:**

| Path under `/config` | Contents | Owner |
|---|---|---|
| `reference-values.json` | the reference value set, `attest/README.md` format | ticket 07 emits, operator places |
| `reference-values.json.sig` | its detached Ed25519 signature, hex, one line (ADR-0006) | same |
| `policy.json` | the sandbox's own signed policy: its egress section and the measurements it will dial (ticket 19, `docs/policy-binding.md`) | ticket 19's build emits, operator places |
| `policy.json.sig` | its detached signature, the same author key under its own domain prefix | same |
| `peers.json` | the peer table | tunneld defines its contents |
| `certificate-chain.bin` | the provisioned certificate chain as an AMD certificate table (VCEK, ASK, ARK), written by `attest/cmd/provision-chain` | ticket 15 |
| `certificate-chain.json` | chip identity and TCB the chain was fetched for, so staleness is detectable (ADR-0005) | ticket 15 |

And inside the measurement, the one trust root:

| Path | Contents |
|---|---|
| `/etc/attested-tunnel/author.pub` | the reference value author's Ed25519 public key, 64 lowercase hex characters and a newline |

`certificate-chain.bin` and `certificate-chain.json` are ticket 15's names and formats
(`attest/provision` writes them; `attest/cmd/provision-chain fetch -out <SRCDIR>` targets the
directory `mkconfigdev.sh` packages). This ticket originally chose `chain/chain.pem`; the
06 boot evidence in `evidence/console-snp.txt` still shows those names. Renaming touched
`mkconfigdev.sh`'s comment block, `tunneld-placeholder.c`'s path constants and this table, and
did not touch the measurement.

Updating any file on the device does not change M. The placeholder demonstrates the
document-alone case ADR-0006 requires: a device with `reference-values.json` and no `.sig`
beside it is reported with the same refusal sentinel as a device with neither.

## Build parameters

`docs/snp/image/build-image.sh`, environment:

| | |
|---|---|
| `AUTHOR_KEY` | required. The reference value author's Ed25519 private key (PEM); its public half is baked in at `/etc/attested-tunnel/author.pub` and the emitted set is signed with it (ticket 07). Rotating it is a new measurement (ADR-0004). |
| `AUTHOR_PUBKEY` | optional cross-check: 32 raw bytes or 64 hex that must equal the public half of `AUTHOR_KEY`. |
| `TUNNELD` | static binary for `/usr/bin/tunneld`. Default: `tunneld-placeholder.c`, built during the build. Ticket 14 sets this and nothing else. |
| `STACK` | ticket 01's host stack (firmware, kernel, modules, edk2 and kernel trees). |
| `OUT` | output directory, default `$STACK/image`. |
| `BUSYBOX` | static busybox, default `/bin/busybox`. |

The build refuses to run if the firmware or kernel hash differs from the pinned value, and
refuses a non-static `TUNNELD` or busybox. It emits `manifest.txt`: hashes of the five
outputs, the verity parameters, the provenance of every input, tool versions, and every
file in the root filesystem and the initrd with its hash and mode.

What "rebuildable and auditable, not bit-reproducible" turned out to mean here: two builds
from the same inputs on this host produced byte-identical `initrd.img` and `rootfs.img`
(timestamps are zeroed, ownership is forced to root, gzip is run with `-n`). The firmware is
the part that is not — it depends on the host's grub package and edk2's own build.

## Procedure

```bash
cd docs/snp/image
bash build-ovmf-amdsev.sh                                # once; ~1 minute on 64 cores
AUTHOR_KEY=/path/to/author.key bash build-image.sh    # ~5 seconds
bash mkconfigdev.sh /path/to/config-src /path/to/config.img
```

Control boot, unprivileged (needs `/dev/kvm`). Boots the image under ticket 01's firmware,
powers off when the placeholder exits, console to the file:

```bash
bash launch-measured-guest.sh -no-snp -config /path/to/config.img -console /tmp/console.txt
```

Confidential boot, as root:

```bash
sudo bash launch-measured-guest.sh -config /path/to/config.img -console /path/to/console.txt
```

Expected on the console, in order: `initrd: verity root hash …`, `initrd: dm-verity mapping
/dev/dm-0 active (panic_on_corruption)`, `initrd: config device /dev/vdb mounted at /config
(ro,noexec,nosuid,nodev)`, `init: dmesg: … SEV: Status: SEV SEV-ES SEV-SNP` (SNP boot only),
`init: sev-guest loaded: report interface at /sys/kernel/config/tsm/report` (SNP boot only;
the control says it did not load, which is the expected diagnostic), `init: no writable path
is executable`, the mount table, then the placeholder's report and `init: tunneld exited with
status 0; powering off`.

### What ran here

Unprivileged control boots, all with the image built from the pinned inputs:

| Config device | Result |
|---|---|
| all five files | root mounted, `/config` mounted `ro,noexec`, no writable path executable, placeholder: set and signature both present, exit 0 |
| `reference-values.json` alone | same boot; placeholder: `REFUSED: reference value set not loadable (document present, signature absent) — ADR-0006`, exit 4 |
| no device | `initrd: WARNING: no config device`; placeholder: `REFUSED … (document absent, signature absent)`, exit 4 |
| one byte flipped in `rootfs.img` data block 200 | `device-mapper: verity: 253:0: data block 200 is corrupted` → `Kernel panic - not syncing: dm-verity device corrupted` |
| four hex digits of `verity.roothash=` changed | `metadata block 339 is corrupted` → same panic, before the root is mounted |

The flipped-byte case mounted the root first and panicked when block 200 was read: verity
is lazy, and the panic is the point of `panic_on_corruption` — a corrupted block is never
returned as an I/O error something might tolerate.

**The confidential boot**, run as root by the operator with the command below, under the
AmdSev firmware with `kernel-hashes=on` (`evidence/qemu-cmdline.txt`). The console
(`evidence/console-snp.txt`) shows, in order: `Memory Encryption Features active: AMD SEV
SEV-ES SEV-SNP`, `SEV: SNP running at VMPL0`, the same five `initrd:` lines as the control,
`sev-guest: Initialized SEV guest driver (using VMPCK0 communication key)`, `init: sev-guest
loaded: report interface at /sys/kernel/config/tsm/report`, `init: no writable path is
executable`, the placeholder finding all five config files, and `reboot: Power down` at
1.18 s. Because the firmware verifies every fw_cfg blob against the hashes table, reaching
`initrd:` at all means the kernel, initrd and command line matched what QEMU measured.

```bash
sudo bash docs/snp/image/launch-measured-guest.sh \
  -image  .scratch/attested-secure-tunnel/host-stack/image \
  -config .scratch/attested-secure-tunnel/host-stack/image-inputs/config.img \
  -console .scratch/attested-secure-tunnel/host-stack/image/console-snp.txt
```

`image-inputs/` holds a throwaway author key generated for the boot tests and dummy config
files; its `README` says so. Neither is a real trust root.

## For ticket 07

Recorded here because this is where the inputs are decided. Ticket 07's result is
`docs/snp-measurement-prediction.md`; `build-image.sh` now also predicts and emits.

- The measured command line is the `-append` string plus its terminating NUL, exactly as
  QEMU hands it to fw_cfg. The firmware appends ` initrd=initrd` for the EFI stub *after*
  verifying the blob, so the string the guest kernel prints differs from the measured one.
- The hashes table is a fixed-layout structure (`PaddedSevHashTable` in `target/i386/sev.c`)
  containing SHA-256 of kernel, initrd and command line, written at the page the firmware
  advertises. Prediction hashes the firmware with that page filled in.
- vCPU count and policy are inputs. `-smp 4`, policy `0x30000`, `cbitpos` and
  `reduced-phys-bits` from CPUID as ticket 01 does.
- `-nodefaults` is set; nothing about the disks or network reaches the measurement.

## What this does not establish

- **The measurement was not read out.** The guest boots and the report interface is present,
  but no report was pulled; that is ticket 07's cross-check, done once, against its prediction.
- **Nothing is verified against the author key.** The placeholder reports presence; the
  loader in `attest/refvalsfile.go` verifies, and it is not in the image until ticket 14.
- **The firmware's bytes depend on the host's grub package.** Recorded, not fixed.
- **Busybox is a distro binary, not a hand-enumerated one.** Recorded above with the
  reasoning.
