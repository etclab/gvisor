# Milestone 1: evidence from real AMD silicon, verified outside its guest. Ticket 05.
# 2026-08-26T03:12Z on shs1, from the branch at 1994c06bf.

## What produced it
docs/snp/verify-on-hardware.sh, in one run, in this order:

  1. sev-snp-measure 0.0.13 predicted the stock guest's launch measurement from the
     firmware image and two launch parameters. No guest, no /dev/sev, no report.
  2. emit-refvals rendered and signed the reference value set naming that prediction,
     and a second set differing from it in one byte of the measurement and nothing else.
  3. acquire-evidence ran as root inside the stock SEV-SNP guest of docs/snp-host-stack.md
     — Linux 6.16.0-snp-guest-038d61fd6422, "Memory Encryption Features active: AMD SEV
     SEV-ES SEV-SNP", VMPL0 — and produced evidence bound to a key it generated a moment
     earlier, bundled with the chain on its config device.
  4. verify-evidence produced verdicts on that evidence, inside `unshare -rn`, in a
     namespace that had just failed to resolve or reach kdsintf.amd.com.

The whole run, including every refusal and the assertions on it, is verify-run.txt.

## Finding: the stale-chain symptom is not the one the documents describe
ADR-0005, docs/provisioning-certificate-chain.md and the comment in attest/verify/snp.go
all say a stale chain surfaces at the peer as *malformed evidence*, because the library
compares the reported TCB against the one the chain was issued for. On real silicon it
does not. AMD derives the VCEK from the chip secret and the TCB together, so the chain for
microcode 71 endorses a different key from the one for 72:

  provisioned (microcode 72)  VCEK public key sha256 6f6da88d1b3f0fa91b01f6747026fa7afad26cc55d80e47750862257bfd5e293
  stale       (microcode 71)  VCEK public key sha256 5887430b44eb7195933037cd4b82f5c8e9a913214063b735163584cdb9523d27

so the report's own signature fails under it and the verdict is *evidence does not chain to
the vendor root*, decided before the coherence check that would have called it malformed
ever runs. Still fail-closed, still no fetch — but an operator told to look for "malformed
evidence" will not find it, and that refusal's detail does not name ADR-0005. See
docs/verification-on-hardware.md, *What this run corrected*.

## What is checked without a guest
attest/hardwareevidence_test.go replays these artifacts on every `go test`: the acceptance,
the substituted-measurement refusal with its control, the missing-chain refusal, and the
stale-chain refusal — against the AMD root certificates embedded in the verification
library, with no hardware and no network. That is a regression guard, not the proof; the
proof is verify-run.txt, because a live guest cannot be replayed.
